## 2. モバイルファーストの画面設計

1. **画面レイアウトのブレークポイント**:
   - `sm`: 640px
   - `md`: 768px
   - `lg`: 1024px（lg以上でPC用サイドバー固定表示、lg未満でスマホ用ヘッダー・ボトムナビ表示）
2. **親指リーチ（Thumb Zone）最適化**:
   - スマホ下部に主要5ナビゲーション（ダッシュボード、検索、記帳[中央強調]、口座、目標、設定）を配置。
3. **スマート入力フォーム**:
   - 数値入力（金額等）は `inputMode="numeric"` を設定し、スマホでテンキーを自動起動。
   - レスポンシブモーダル（スマホでは下部/中央にコンパクト表示、PCでは適切な幅でセンタリング）。
4. **PC用サイドバー (`Sidebar.tsx`) のビューポート高固定・下部アクション常時表示**:
   - PC表示（`lg` 以上 / `1024px` 以上）の左サイドバーは、メインエリアの縦長に連動して引き伸ばされないよう、高さをウィンドウ1画面分（`h-screen` / `h-dvh`）に固定し、`sticky top-0`（および `self-start` / `shrink-0`）で画面左端に常時追従表示とする。
   - メインエリアが縦に長くスクロールが発生した場合でも、サイドバーは常にウィンドウの高さに収まり、最下部の「ユーザー情報・CSVダウンロードボタン・ログアウトボタン」へメイン画面のスクロール不要で即座にアクセスできること。
   - ウィンドウの縦幅が狭いPC画面等でサイドバー内のコンテンツが1画面に入りきらない場合は、上部エリア（ロゴ・ナビゲーション・テーマ切替・言語切替）を内部縦スクロール可能（`min-h-0 flex-1 overflow-y-auto`）とし、最下部の「ユーザー情報・CSVダウンロードボタン・ログアウトボタン」領域は `shrink-0` で常にサイドバー下端へ固定表示する。

## 3. ゲーミフィケーション・モチベーション向上UI設計

1. **こまめ草生やし（Activity Bean Heatmap）**:
   - 直近4週間（28日間）の実際の明細登録件数マップ（`txCountByDate`）に基づく曜日別カレンダーマトリックス。
   - 件数に応じた4段階の濃淡（0件: 透過/空, 1件: 薄緑, 2件: 中緑, 3件以上: 濃緑）。
   - 本日セルのリングハイライト、未来日付の透過・薄色表示。
   - 連続記録ストリーク日数バッジ（`🔥 ○日連続こまめ記録中` または `🔥 今日からこまめに記録！`）を動的表示。
2. **まめの樹（Bean Sprout）育成システム**:
   - 貯蓄目標の総合達成率（`overallProgressRate`）および記帳継続ストリーク日数（`streakDays`）に連動した4段階ステージ動的遷移：
     - ステージ 1: はじまりの種 🌰
     - ステージ 2: かわいい双葉 🌱
     - ステージ 3: すくすく新芽 🌿
     - ステージ 4: 豊かな実り 🌳
   - 4ステップのステージ進捗インジケーター、現在ステージバッジ、次の進化条件のリアルタイム表示。
3. **やさしいスマート・アドバイス（ポジティブフィードバック）**:
   - 今月と先月の明細比較（前月比節約費目・最大節約額の自動算出）。
   - 今月の月間収支（黒字額）や目標達成ペースの試算、記帳ストリークを称える励ましメッセージを動的生成。
4. **貯蓄目標の進捗一覧・編集・削除・アーカイブUI (`GoalsTab.tsx` / 要件 17-2)**:
   - **合算進捗（全体達成率）の集計ルール**:
     - 「全目標の合算進捗（全体達成率）」サマリーバナー、「まめの樹育成システム」の総合達成率（`overallProgressRate`）、および「やさしいスマート・アドバイス」の目標進捗判定は、**現在進行中（未アーカイブ：`isArchived === false`）の目標のみ**を集計対象とし、アーカイブ済み目標は集計から除外する。
   - **各目標カードのアクションボタン**:
     - **編集ボタン**: 進行中の目標（未達成・達成済み共通）に対して「編集」ボタンを配置。押下時に目標編集モーダル（または新規作成と共通化されたフォームモーダル）を開き、タイトル・目標金額・達成予定日・集計対象口座・テーマカラーを編集・保存できる。
     - **削除ボタン（未達成目標のみ）**: 未達成（達成率100%未満 かつ `isCompleted === false`）の目標カードには「削除」ボタンを配置。誤操作防止のため確認ダイアログ（またはインライン確認UI）を表示した上で `DELETE /api/goals?id=...` を実行する。
     - **アーカイブボタン（達成済み目標のみ）**: 達成済み（達成率100%以上 または `isCompleted === true`）の目標カードには削除ボタンを表示せず（削除不可として保護）、代わりに「アーカイブ」ボタンを配置。押下時に `PUT /api/goals`（`action: "archive"`）を実行し、進行中一覧からアーカイブ一覧へ移動させる。
   - **アーカイブ済み目標の表示トグルと復元UI**:
     - 貯蓄目標の進捗一覧セクション内（ヘッダーまたは一覧下部）に「アーカイブ済みを表示（N件）」トグルボタンを配置。
     - トグル展開時、アーカイブ済みの達成目標カードを一覧表示する。各アーカイブ済みカードには「復元（進行中に戻す）」ボタンを配置し、押下時に `PUT /api/goals`（`action: "restore"`）を実行して進行中一覧へ戻せるようにする。アーカイブ済みカードには削除ボタンを表示せず、達成履歴を保護する。

## 4. 記帳タブ (`RegisterTab.tsx`) の3大入力モード

| モードID | 名称 | 想定ユースケース | 入力構成 |
| :--- | :--- | :--- | :--- |
| `single` | **1件ずつ登録** | 都度払いや日々のこまめな支出記録 | 日付、店舗名（履歴提案連動）、金額、費目、支払手段、メモ、タグ、貯蓄先口座（投資時） |
| `shop_batch` | **同店舗一括** | 1枚の店舗レシートの内訳登録（例: スーパーで食材と日用品を同時購入） | 日付（共通）、店舗名（共通）、支払手段（共通）、内訳明細行（費目・金額・メモ） × N行、合計金額 |
| `category_batch` | **同費目一括** | 週末等に同一費目（食費等）の複数レシートを一括記録 | 費目（固定）、支払手段（共通）、内訳明細行（日付・店舗名・金額・メモ） × N行、合計金額 |

### 一時保存（ドラフト）連携
- 手動保存 (`manualDraft`) / 自動保存 (`autoDraft`) ともに、モードごとの複数行構造（`batchRows`, `categoryBatchRows`）および合計件数・金額を完全に復元可能。

### 離脱時ガード（未保存警告: 要件 2-5）
- フォームに入力途中の値（金額・店舗名・メモ・一括行など）がある状態で、タブ切り替え（サイドバー・ボトムナビ等）やブラウザの閉じる/リロードを試みた場合、警告モーダル（`LeaveGuardModal.tsx`）またはブラウザ標準警告ダイアログ（`beforeunload`）を表示。
- 未入力時（`isFormDirty === false`）は確認ダイアログを表示せず即時遷移。
- 破棄確認時は自動退避ドラフト（`auto`）を削除し、指定先タブへ安全に遷移。

### 単価×個数 金額計算補助UI（インライン展開方式: 要件 2-7）
- **対象箇所**: 記帳タブ（`RegisterTab.tsx`）の支出登録全モード（`single` / `shop_batch` 各行 / `category_batch` 各行）および明細編集モーダル（`EditTransactionModal.tsx`）の支出編集時の金額入力欄。
- **トリガーボタン**: 各金額入力欄の横またはラベル横に「計算（電卓 / `×` アイコン）」トグルボタンを配置。通常時は折りたたまれた状態をデフォルトとし、既存のシンプルな入力レイアウトを維持する。
- **インライン展開パネル**:
  - トグルボタン押下で該当金額入力欄の直下（一括登録では該当行の直下/行内）に `単価` × `個数` のコンパクトな入力UIを展開表示する。
  - `単価` フィールドには `inputMode="numeric"` を設定し、スマートフォンでもテンキーで素早く入力できるようにする。
  - `個数` フィールドは `1` 〜 `30` の整数を選択するセレクトボックス（初期値 `1`）とする（31個以上が必要な場合は金額入力欄へ直接手入力する）。
  - 一括登録モード（`shop_batch`, `category_batch`）では行ごとに独立して展開・折りたたみ・計算が行える構造とする。
- **計算・反映と手動編集の挙動**:
  - `個数` の初期値が `1` であるため、`単価` に正の整数を入力した時点で即座に `単価 × 個数` が算出され、金額入力欄へ自動反映される。`個数` セレクトボックスを変更した際もリアルタイムで再計算・反映される（取引金額上限 `9,999,999,999` を超過する場合はエラー/警告を表示し上限外の値を反映しない）。
  - 計算補助パネルを折りたたんだ後も、金額欄へ反映済みの値は保持される。また、金額入力欄を直接手入力で編集した場合は手動入力値を優先して保持する。

### 定例支払いテンプレート管理 & 自動支払い予定UI（記帳タブ内: 要件 2-8）
- **配置場所**: 記帳タブ（`RegisterTab.tsx`）内に「定例支払いテンプレート管理」セクション（または展開パネル/モーダル）を配置し、世帯メンバー全員（管理者・一般メンバー共通）が操作できるようにする。
- **テンプレート登録・編集フォーム**:
  - **取引種別切替**: 「定例支出（クレカ・口座引き落とし・積立投資等）」と「定例口座間振替（資金移動）」の2種別を選択可能。
  - **支払日（引き落とし日）設定UI**:
    - 決済手段として**クレジットカード**を選択した場合：そのカードに設定されている「引き落とし日（毎月◯日）」を自動表示し、「※カードの引き落とし日（支払日）の翌日に、次回サイクル分の支払い予定明細が自動追加されます」と案内を表示する（ユーザーによる日付手入力は不要）。
    - **口座引き落とし（口座振替）・その他決済手段・口座間振替**を選択した場合：「毎月の引き落とし日・振替日」セレクトボックス（`1日`〜`28日`、および `月末(99)`）を表示し、任意の日を指定できるようにする（「※指定した支払日の翌日に次回サイクル分の支払い予定明細が自動追加されます」と案内表示）。
- **テンプレート一覧カード表示と操作**:
  - 登録済みテンプレートごとに、名称、金額、種別バッジ（支出/振替）、費目・決済手段（または移動元→移動先口座）、毎月の支払予定日（次回自動追加タイミング）、および最終生成サイクル（`YYYY-MM`）を表示。
  - 各テンプレートカードに「編集」ボタン、「有効/一時停止」トグル、および「削除」ボタンを配置。
- **自動追加された「支払い予定（未精算）」明細の表示と精算連動**:
  - アプリ起動・データ取得時に月次同期（`/api/recurring-templates?autoSync=true` 等）を実行し、新規サイクル分が自動追加または支払日到来分が自動精算された場合はトースト等で分かりやすく通知する。
  - 未精算（`isSettled === false`）の支払い予定明細は、明細一覧やテンプレート管理セクションから「支払い予定（未精算・予定日 YYYY-MM-DD）」として識別でき、必要に応じて手動で「今すぐ精算（残高へ反映）」を実行することも可能とする。

## 5. クレジットカード引き落とし予定額 & 3段階原資シグナル表示 (要件 9)

ダッシュボード上部に配置されるカードアラートセクション。登録されている有効なクレジットカードごとに、未精算明細・引き落とし予定日・引き落とし元口座の残高を動的にリアルタイム突合。

1. **3段階シグナル判定**:
   - **充足 (sufficient / 緑バッジ)**: 引き落とし元口座の実質利用可能残高（ロック除外）が予定額以上。原資準備OK。
   - **注意 (warning / 橙バッジ)**: 口座の総残高は予定額以上だが、貯蓄ロック（reservedAmount）を差し引いた利用可能残高が不足。貯蓄枠の取崩しまたは口座充当を案内。
   - **不足 (shortage / 赤バッジ)**: 口座の総残高そのものが予定額未満。口座への資金移動・入金が必要。不足金額を明示。
2. **複数カード対応**:
   - クレジットカード切り替えセレクターピル（カード名・予定額・状態ドット）により各カードをスムーズに切り替え。全カード合計予定額も併記。

### 5.1 口座・決済手段の種別表示名称マッピング (`AccountsTab.tsx`, `AddAccountModal.tsx`, `EditPaymentMethodModal.tsx`)

決済手段の追加・編集モーダルの種別セレクトおよび口座タブの種別バッジにおいて、DB内部値（`payment_methods.type`）とUI表示名称の対応を以下の通り統一する。

| DB内部値 (`payment_methods.type`) | UI表示名称 | 追加・編集モーダル選択肢 | 引き落とし元口座の選択制約 |
| :--- | :--- | :---: | :--- |
| `credit_card` | クレジットカード | あり | 銀行口座 (`bank`) のみ |
| `qr_code` | QR・バーコード決済 | あり | 銀行口座 (`bank`) またはプリペイドウォレット (`prepaid_wallet`) |
| `debit_card` | **引落・デビットカード** | あり | 銀行口座 (`bank`) のみ |
| `direct_debit` *(既存互換)* | **引落・デビットカード** | なし（※編集時は `debit_card` として扱い統一） | 銀行口座 (`bank`) のみ |
| `cash` | 現金 | あり | 手元現金 (`cash`) のみ |

- **既存挙動の維持**: 「引落・デビットカード」（`debit_card` / `direct_debit`）は、通常明細登録時の即時減額・定例支払いテンプレート時の任意指定引き落とし日連動など既存の会計ロジックを変更せず維持する。

   - 各世帯行/カードに、世帯名、申請者メールアドレス、申請日時、ステータスバッジ（`承認待ち` / `承認済み` / `却下` / `停止中`）、審査日時・却下理由（ある場合）を表示。
   - 状態に応じた操作アクション：
     - `pending`（承認待ち）: 「許可（承認）」ボタン、「却下」ボタン（任意の却下理由入力対応）
     - `rejected`（却下済み）: 「再承認」ボタン、「削除（抹消）」ボタン（確認ダイアログ付き）
     - `approved`（承認済み）: 「利用停止」ボタン（現在ログイン中の自世帯は停止不可の保護表示）
     - `suspended`（停止中）: 「利用再開」ボタン
6. **ログイン・新規世帯申請画面UI (`src/app/page.tsx`)**:
   - 新規世帯登録タブのボタン文言を「新規世帯の登録を申請する」等とし、「※システム管理者の承認後にログイン可能となります」の案内テキストを表示。
   - 申請送信成功時（`pendingApproval: true`）はダッシュボードへ遷移せず、申請受付完了バナーを表示してログイン画面へ誘導する。
   - 承認待ち・却下・停止状態でログインを試行した際は、APIから返却された状態メッセージをエラー/案内アラートとして表示する。
   - **初期デモ管理者アカウント欄のテスト環境限定出力**:
     - ログイン画面下部の「💡 初期デモ管理者アカウント（`admin@komame.local` / `Password123!` および『クイック入力』ボタン）」欄は、テスト環境（`process.env.NODE_ENV !== "production"`）でのみ出力し、本番環境（`process.env.NODE_ENV === "production"`）では一切出力しない。
