# 『Komame』詳細要件仕様書

## 1. ロール・権限構造

本システムはマルチテナント型家庭用家計簿であり、以下の3つのロールで構成される。

| ロール | 想定対象 | 主な利用可能機能 | 権限レベル |
| :--- | :--- | :--- | :--- |
| **最上位管理者 (Super Admin)** | システム運営者 | システム全体の稼働監視、新規世帯登録申請の承認・却下・再承認・抹消、世帯アカウントの停止・再有効化 | 全体 |
| **家庭管理者 (Household Admin)** | 世帯主・家計の主管理者 | 家族メンバーの招待・管理、パスワード要件設定、費目マスター管理（追加・編集・並び替え・アーカイブ/復元）、24時間チェックポイントリバート実行、家庭内全操作ログ閲覧・特定条件エクスポート、CSVフルインポート・エクスポート、全家計簿機能 | 世帯管理者 |
| **家庭メンバー (Household Member)** | 家族・パートナー | 1件/店舗一括/費目一括明細登録、定例支払いテンプレート管理（追加・編集・一時停止・削除・自動支払い予定追加）、一時保存（手動/自動）、ダッシュボード閲覧、口座残高・カード引き落とし予定確認、貯蓄目標管理（追加・編集・未達成目標の削除・達成済み目標のアーカイブ/復元）・草生やし、個別CSVエクスポート | 世帯一般 |

### 複数家庭所属への拡張性（先行N:M互換設計）
- 初期リリース時は「1ユーザー = 1世帯に所属」として運用。
- 内部データモデルは `users` - `household_memberships` - `households` の多対多構造（N:M）で構築されており、将来複数世帯の切り替え機能を追加する場合もDBスキーマ変更不要で移行可能。

## 2. 機能要件一覧

### 【要件 1】認証・セキュリティ・世帯サインアップ（申請・許可制）
- **1-1. ログイン/ログアウト**:
  - メールアドレスとパスワードによる認証。
  - パスワード検証成功後、所属世帯の承認ステータス（`households.status`）を確認し、`approved` の場合のみセッションを発行する。`pending`（承認待ち）、`rejected`（却下）、`suspended`（停止中）の場合はログインを拒否し、状態を明示した案内メッセージ（`403 Forbidden`）を表示する（パスワード誤り・未登録メール時はアカウント列挙防止のため従来通り `401` を返却）。
- **1-2. セルフサインアップ（申請・許可制） & 家族招待**:
  - **新規世帯登録申請**: ログイン画面の「新規世帯登録」は申請・許可制とする。入力項目は従来通り「メールアドレス」「パスワード」「世帯名」の3項目とし、申請時は `public` スキーマのみに承認待ち（`pending`）状態で保存する。申請時点ではテナント専用スキーマの作成やセッションCookieの発行を行わない。
  - **システム管理者（Super Admin）による承認・却下・停止**:
    - `is_super_admin = true` のシステム管理者は、管理タブ内のシステム管理セクションから申請一覧（承認待ち・承認済み・却下・停止）を確認できる。
    - **承認（許可）時**: 世帯ステータスを `approved` に更新し、この時点で初めてテナント専用スキーマ（`tenant_{household_id}`）、初期設定、標準12費目マスター、デフォルト現金口座を作成してログイン可能にする。
    - **却下時**: 世帯ステータスを `rejected` として記録を残す。システム管理者は後から却下済み申請を再承認（`approved` へ変更・スキーマ初期化）または物理削除（抹消して同メールでの再申請を可能化）できる。
    - **停止・再有効化**: 承認済み世帯の停止（`suspended`）および利用再開（`approved`）を行える。
  - **家族招待**: 承認済み世帯の家庭管理者（`Household Admin`）が発行する招待リンクやメンバー登録による家族の参加は、従来通りシステム管理者の追加許可不要で即時有効・ログイン可能とする。
- **1-3. パスワードポリシー動的設定**:
  - 管理者画面で「最小文字数」「英大文字・小文字・数字・特殊文字の必須有無」を設定可能。新規サインアップ・招待参加・パスワード変更時に動的検証。
  - パスワードハッシュ化は `Argon2id` を採用。
- **1-4. セッション管理**: Secure / HttpOnly Cookie + JWT (HS256) によるセキュアな世帯コンテキスト伝播。
- **1-5. 動的テナントスキーマ名ホワイトリスト検証**: テナントスキーマ名（`tenant_{household_id}`）に対する正規表現ホワイトリスト検証（`/^tenant_[a-zA-Z0-9_-]{1,55}$/`）を全DB接続で強制し、SQLインジェクションを完全根絶。
- **1-6. レートリミッター (ブルートフォース・DoS防御)**: ログイン・サインアップ申請・招待APIにスライディングウィンドウ方式のレートリミットを適用（超過時は `429 Too Many Requests`）。
- **1-7. HTTP セキュリティヘッダー & CSRF 多層防御**: `X-Frame-Options: DENY`、`nosniff`、`CSP` 等の適用および状態変更API（POST/PUT/DELETE）での `Origin` / `Host` 検証。
- **1-8. DB突合リアルタイム認可 & セッション即時失効**: ログアウト時やパスワード更新時のトークン失効、および毎リクエスト時のアカウント有効状態・世帯承認ステータス（`households.status === "approved"`）・最新ロールのDB突合検証。
- **1-9. 初期デモ管理者アカウントのテスト環境限定有効化**:
  - **テスト環境の定義**: `NODE_ENV !== "production"`（`development` および `test` の非本番環境すべて）をテスト環境とみなす。
  - **認証・セッションでの本番無効化**: 初期デモ管理者アカウント（メールアドレス `admin@komame.local` またはデモ固定ユーザーID `usr-yamada-taro-001`）はテスト環境でのみ有効とする。本番環境（`NODE_ENV === "production"`）においては、`POST /api/auth/login` でのログイン試行を拒否（`401 Unauthorized`）し、`getCurrentSession()` でもセッションを無効（`null`）として遮断する。
  - **本番シードでの作成禁止**: 本番環境（`NODE_ENV === "production"`）でのシード実行時（`npm run db:seed`）に、初期デモ管理者アカウント（`admin@komame.local` / `Password123!`）を作成することを禁止する（本番環境でデモ資格情報が指定またはフォールバックされた場合はエラーで停止する）。また、`docker-compose.prod.yml` 等の本番構成ファイルからもデモ資格情報のデフォルトフォールバックを排除する。
  - **ログイン画面UIのテスト環境限定出力**: ログイン画面（`src/app/page.tsx`）の「初期デモ管理者アカウント（メールアドレス・パスワード表示およびクイック入力ボタン）」欄は、テスト環境（`NODE_ENV !== "production"`）でのみ出力し、本番環境（`NODE_ENV === "production"`）では一切出力しない。

### 【要件 2 & 5】明細登録・資金移動・サジェスト
- **2-1. 1件ずつの明細登録**: 日付、金額、費目、支払手段、店舗・取引先名、簡易メモ、資金移動先口座（貯蓄・投資時）。
- **2-2. 同じ店舗に対する一括登録画面 (`shop_batch`)**: 1枚のレシートから複数行の品目・費目・金額を行追加して一括登録。
- **2-3. 同じ費目に対する一括登録画面 (`category_batch`)**: 同一費目（例: 食費）について複数店舗・日付・金額を連続登録。
- **2-4. タグ付け & カラーラベリング**: 支出や資金移動に色付きタグ（`#固定費`, `#自己投資`等）を付与。
- **2-5. 離脱時ガード（未保存警告）**: フォームに入力途中の値がある状態で画面遷移やタブ閉じを試みた場合、確認ダイアログを表示（未入力時は即時遷移）。
- **2-6. 簡易メモ機能**: レシート表記と実際の商品名の相違や個数を記録。
- **2-7. 単価×個数 金額計算補助（入力支援機能）**:
  - **概要**: 支出の金額入力欄において、単価と個数から合計金額（`単価 × 個数`）を計算し、金額入力欄へ直接反映できる入力支援機能を提供する。
  - **対象画面・モード**: 支出を扱うすべての金額入力欄を対象とする（記帳タブ `RegisterTab.tsx` の「1件ずつ登録 (`single`) ※支出タブ時」「同店舗一括 (`shop_batch`) の各明細行」「同費目一括 (`category_batch`) の各明細行」、および明細編集モーダル `EditTransactionModal.tsx` の支出明細編集時）。
  - **データ保持・スコープ**: DBスキーマ（`transactions` 等）やAPIペイロードへの単価・個数カラム追加は行わず、算出された合計金額のみを金額入力欄へセットする純粋な入力支援機能とする。メモ欄への自動追記、消費税計算、複数品目合算機能は含まない。
  - **入力制約・境界値**:
    - 単価は正の整数（半角数字、`inputMode="numeric"`）のみ受け付ける。
    - 個数UIは `1` 〜 `30` の整数を選択するセレクトボックス（初期値 `1`）とし、31個以上を購入する場合は金額入力欄へ直接手入力する運用とする（なお、計算ヘルパー関数 `calculateUnitTotal` 自体は `1` 以上の正の整数を受け付ける汎用仕様を維持する）。
    - 計算結果が取引金額の許容範囲（`1 <= 合計金額 <= 9,999,999,999`）に収まることを検証する（上限超過時は警告表示等により不正値のセットを防止する）。
  - **既存機能連携**: 金額欄へ反映された合計金額は、一括登録の合計金額表示・離脱時ガード（未保存警告）・自動一時保存（2秒デバウンス）にも通常の金額入力と同様に連動する。
- **2-8. 定例支払い（月次固定費・振替）テンプレート管理 & 自動支払い予定明細追加**:
  - **概要**: クレジットカードや口座引き落とし（口座振替）、積立投資、口座間資金移動などで毎月決まった額を支払うものをテンプレート化し、月次の支払いサイクルが始まるごとに自動で「支払い予定（未精算明細）」として明細一覧へ追加する機能を提供する。
  - **配置場所と操作権限**:
    - 「記帳」タブ（`RegisterTab.tsx`）内に「定例支払いテンプレート管理」セクションを配置する。
    - 世帯メンバー全員（`Household Admin` および `Household Member`）がテンプレートの作成・編集・有効/無効（一時停止）切替・削除を行える。
  - **対象取引種別とテンプレート項目**:
    - **支出 (`expense`)**: 店舗・取引先名（テンプレート名）、金額（`1 <= amount <= 9,999,999,999` の整数）、費目、決済手段（クレジットカード、口座振替、デビット、QR、現金等）、積立・投資時の移動先口座（`to_account_id`、任意）、毎月の支払日（引き落とし日）、メモ、有効フラグ（`is_active`）。
    - **口座間振替 (`transfer`)**: 振替名称（テンプレート名）、金額（`1 <= amount <= 9,999,999,999` の整数）、出金元口座（`from_account_id`）、入金先口座（`to_account_id`）、毎月の振替日（引き落とし日）、メモ、有効フラグ（`is_active`）。
  - **支払日（引き落とし日）の規定と「支払日の翌日」自動追加ルール**:
    - **クレジットカード決済の場合**: 選択されたクレジットカードに規定されている「引き落とし日（`payment_methods.withdrawal_day`、未設定時は27日）」を基準日（`D` 日）として自動適用する。毎月のカード引き落とし日（支払日）の**翌日（`D + 1` 日、月末引き落としの場合は翌月1日）**に次の月次支払いサイクルが開始され、次回引き落としサイクル分の「支払い予定」明細が自動追加される。
    - **口座引き落とし・その他決済・口座間振替の場合**: テンプレートごとに任意の「毎月の引き落とし日・振替日（`1`〜`28`日 または `99`: 月末）」を指定する。指定された引き落とし日の**翌日（`D + 1` 日、月末指定時は翌月1日）**に次回サイクル分の「支払い予定」明細が自動追加される（なお、テンプレート新規作成時点で当月の支払日 `D` 日がまだ到来していない場合は、当月サイクル分を初回自動生成する）。
    - **二重生成防止**: テンプレートごとに対象サイクル年月（`last_generated_month: 'YYYY-MM'`）を記録・突合し、同一サイクル月の明細が重複して追加されないよう冪等性を保証する。
  - **「支払い予定（未精算）」の口座残高反映タイミング**:
    - **クレジットカード**: 既存のクレジットカード明細と同様に未精算（`is_settled = false`、`scheduled_withdrawal_date` に引き落とし予定日を計上）として追加され、ダッシュボードの次回カード引き落とし予定額・原資チェック（要件 9）へ自動合算される。
    - **口座引き落とし・即時決済手段・積立投資・口座間振替**: 自動追加された時点では支払日到来前の「支払い予定（未精算：`is_settled = false`、`scheduled_withdrawal_date` に支払予定日を設定、口座残高はまだ減額・移動しない）」として明細追加される。その後、**支払予定日（`scheduled_withdrawal_date`）の当日が到来した時点（自動同期時）、またはユーザーが画面上で手動確定（「今すぐ精算」）を実行した時点**で `is_settled = true` に更新され、口座残高の減額・移動（および積立投資時の受入明細生成）が反映される。
  - **監査ログ連携**: テンプレートの作成・編集・有効/無効切替・削除、および自動明細生成・精算処理を監査ログ（`audit_logs`）に記録する。
- **5. 機械的サジェスト機能**: 店舗名入力時に過去履歴から店舗名を補完し、決定時に最も使われた「費目」「支払元」を自動提案（1タップ適用）。

### 【要件 6】2段階の一時保存機能（明示的 & 自動保存）
- **6-1. 手動一時保存 (Manual Draft)**: 「一時保存」ボタン押下で保存（1件保持、上書き時は警告表示）。
- **6-2. 自動一時保存 (Auto Draft)**: キー入力停止後2秒（デバウンス）で自動退避。画面右下に控えめなトーストを表示。
- **6-3. 再開メニュー**: 登録画面トップに手動・自動保存日時・金額等を比較表示し、ワンタップで復元。
- **6-4. 警告表示**: 手動保存データがある状態で新規登録を完了しようとする場合、手動下書きデータが破棄される旨の警告確認モーダルを表示。

### 【要件 8, 9, 10, 11, 12, 18】口座・決済手段・資金フロー・色分け管理
- **8 & 10. 口座・カード・決済手段の登録**:
  - 銀行口座（普通・定期）、プリペイドウォレット（PayPay、Suica等）、クレジットカード、デビットカード、現金を登録。
  - クレジットカードには「締め日（1〜28日 / 99:月末）」、「引き落とし日（1〜28日 / 99:月末）」、「引き落とし月オフセット（0:当月 / 1:翌月 / 2:翌々月）」、「引き落とし元口座」を設定。
- **11. 残高管理 & 会計連動ロジック**:
  - 即時決済（現金、デビットカード、QR残高払い）: 登録と同時に該当口座・ウォレット残高が即時減額。
  - クレジットカード払い: 登録時点では銀行口座残高は減少しない（未精算として引き落とし予定日に計上）。
  - 口座間振替（transfer）: 出金元口座を減額し、入金先口座を加算。
  - 貯蓄・投資（NISA・定期預金）支出: 出金元口座を減額し、指定された投資先口座へ同額加算（受入明細を自動生成）。
  - **金額・残高境界値検証 (VULN-09)**: 取引金額は `1 <= amount <= 9,999,999,999` の整数、口座残高は `0 <= balance <= 9,999,999,999` の整数に限定し、範囲外や小数は拒否。
  - **DBトランザクション原子性**: 複数口座・明細・受入振替が連動する更新は `db.transaction()` で保護し、例外時は完全ロールバック。
- **9. クレジットカード引き落とし予定額・原資チェック**:
  - 次回引き落とし予定額を集計し、紐づく銀行口座の現在残高と比較して「原資充足」または「不足（あと〇〇円不足）」を警告。
- **12. 資金フローの可視化**: 口座引き落とし、窓口引き出し、カード決済、チャージ、投資振替を一元追跡。
- **18. 口座内での疑似的な資金色分け（バーチャル貯蓄・取り分け）**:
  - 口座残高の一部を特定用途（車検用・生活防衛資金等）としてバーチャルにロック。
  - 「実質利用可能残高 = 現在残高 - ロック金額合計」を算出・表示。

### 【要件 4】費目管理（マスターID管理 & 初期プリセット & メンテナンス機能）
- **4-1. マスターID管理と初期プリセット**:
  - 費目は内部IDで管理。DBスキーマ上は階層構造（`parentId`）を保持し、メンテナンス画面ではフラット（1階層）管理とする。
  - 費目名やアイコン・カラーを変更しても、過去の全明細および集計グラフが再登録不要で即座に連動反映。
  - 新規世帯開設時に日本の標準家計簿プリセット（食費、外食、日用品、住居費等12種）を自動シード投入（`is_system = true`）。
- **4-2. 費目メンテナンス機能（家庭管理者 `admin` 限定）**:
  - **配置場所**: 管理タブ（`AdminTab`）内に「費目マスター管理」セクションを配置。
  - **標準12費目の保護**: 初期プリセット12種は保護対象とし、名前・アイコン・カラーの編集およびアーカイブ（論理削除）は不可とする。
  - **ユーザー追加費目の追加・編集・アーカイブ・復元**:
    - 新規費目の追加（費目名、アイコン、カラー）。
    - ユーザー追加費目の編集（費目名、アイコン、カラー）。
    - ユーザー追加費目のアーカイブ（論理削除）およびアーカイブ済み費目の一覧表示・復元（アンアーカイブ）。
  - **並び順変更**: 標準12費目を含む全費目を対象に表示順の並び替えを可能とする。
  - **アーカイブ時の表示方針**: アーカイブ済み費目は新規明細登録時の選択肢から除外しつつ、過去の明細一覧・検索結果・集計グラフ等では名称・アイコン・カラーを維持表示する。
  - **監査ログ連携**: 費目の追加・編集・並び替え・アーカイブ・復元の各操作を監査ログ（`audit_logs`）に記録する。

### 【要件 7】データインポート・エクスポート (CSV)
- **文字コード**: 日本のExcelで文字化けしない **UTF-8 (BOM付き)**。
- **数式インジェクション防御 (VULN-07)**: 数式トリガー文字（`=`, `+`, `-`, `@`, `\t`, `\r`）から始まる文字列セルにシングルクォートを付与して無害化（負の数値型はそのまま出力）。RFC 4180 準拠エスケープ。
- **エクスポート**: 全明細CSVおよび口座一覧CSV出力。フルエクスポートは管理者権限限定。
- **インポート**: 家計簿明細CSVの取り込み（カラムマッピング、同一日・店舗・金額の重複候補警告）。管理者限定。最大5MB・5,000行制限。

### 【要件 14, 15, 17, 17-2】ダッシュボード・統計・目標・検索
- **14. ダッシュボード**: 総資産、実質利用可能残高、貯蓄ロック額、次回クレカ引き落としアラート、費目別比率バー、最近の明細。
- **15. 単純検索**: 収支種別（全明細 / 支出のみ / 収入のみ / 資金移動のみ）、費目、決済手段、期間、キーワードによる絞り込み。実質収入・実質支出・純貯蓄のスマート集計。
- **17. 収入登録**: 額面給与、税金・社保控除額、手取り入金先口座、臨時収入フラグ。
- **17-2. 貯蓄目標管理**:
  - **進捗可視化**: 複数貯蓄口座を合算/単独で目標額に対する達成率（%）と残り金額を自動計算・可視化。
  - **操作権限**: 世帯メンバー全員（`Household Admin` および `Household Member`）が目標の追加・編集・削除・アーカイブ・復元を実行可能とする。
  - **目標の追加・編集**: 目標タイトル、目標金額（`1 <= targetAmount <= 9,999,999,999` の正の整数）、目標達成予定日（任意）、集計対象口座（複数選択可）、テーマカラーを設定・編集可能とする。
  - **未達成目標の削除**: 未達成（達成率100%未満 かつ `is_completed = false` かつ未アーカイブ）の目標は物理削除を可能とする。
  - **達成済み目標の削除禁止とアーカイブ・復元**:
    - 達成済み（達成率100%以上 または `is_completed = true`）の目標、およびアーカイブ済み（`is_archived = true`）の目標は削除不可として保護し、代わりにアーカイブ（`is_archived = true`）を可能とする。
    - 一覧内に「アーカイブ済みを表示」トグルを設け、アーカイブした達成済み目標の履歴閲覧および元の進行中一覧への復元（アーカイブ解除：`is_archived = false`）を可能とする（アーカイブ後も削除は不可のまま保護）。
  - **合算進捗（全体達成率）の集計対象**: アーカイブ済みの目標（`is_archived = true`）は「全目標の合算進捗（全体達成率）」および「まめの樹育成システム」「やさしいアドバイス」の集計対象から除外し、現在進行中（未アーカイブ）の目標のみで合算進捗・全体達成率を計算する。
  - **監査ログ連携**: 目標の作成・編集・アーカイブ・復元・削除の各操作を監査ログ（`audit_logs`）に記録する。

### 【要件 16】ゲーミフィケーション・モチベーション向上
- **こまめ草生やし（Activity Bean Heatmap）**: 記帳した日の濃淡マトリックスとストリーク日数表示。
- **まめの樹（Bean Sprout）育成**: 記録や貯蓄目標達成に応じた新芽の成長インタラクション。
- **やさしいほめ言葉・アドバイス**: 予算達成時や節約時の前向きなメッセージ。

### 【要件 3, 21, 22】管理者機能・操作ログ・24時間チェックポイントリバート
- **3-1 & 21. 操作ログ**: いつ・誰が・どの画面で何のデータを登録/更新/削除したかを記録。
- **3-2. ユーザー管理**: 家族メンバーの招待、権限変更、パスワードリセット、無効化。
- **3-3. 条件付きログエクスポート**: ユーザー・期間・操作種別を指定してCSV/JSON出力。
- **3-4. システム設定**: 通貨表示（¥ / $ / €）、日付フォーマット、パスワード強度ポリシー。
- **22. 24時間チェックポイントリバート**:
  - トランザクションごとにチェックポイントを作成（有効期限24時間）。
  - 指定時点以降の明細データおよび連動した口座残高を該当状態にロールバック。
  - **一時保存データのリセット**: リバート実行時、`drafts` テーブルを物理削除して空に初期化。
  - **家族影響警告**: 同一世帯の他メンバーが登録した明細への影響サマリーを表示し、7文字のランダム確認コード入力による二重確認を必須化。

## 3. データ削除ポリシー

| 対象データ | 削除方式 | 具体的挙動 |
| :--- | :---: | :--- |
| **費目マスター (`categories`)** | **論理削除 (アーカイブ)** | `is_archived = true` となり新規選択肢から非表示。過去明細やグラフは維持。 |
| **口座・決済手段 (`accounts`, `payment_methods`)** | **論理削除 (非活性化)** | `is_active = false` となり新規選択肢から非表示。過去の決済履歴は維持。 |
| **家族ユーザー (`household_memberships`)** | **論理削除 (無効化)** | ステータスを `inactive` にしてログイン遮断。過去の登録履歴は記録保持。 |
| **支出・収入明細 (`transactions`)** | **論理削除 / ログ退避** | 画面・残高から即時除外。`audit_logs` に退避され、24hリバート時はログから復元可能。 |
| **一時保存データ (`drafts`)** | **物理削除** | 一時作業データのため、破棄・上書き・リバート時はDBから物理削除。 |
| **定例支払いテンプレート (`recurring_templates`)** | **一時停止 (`is_active = false`) / 物理削除** | 一時停止時は自動生成を停止しつつ設定を保持。削除時はテンプレートレコードを物理削除（既に自動生成済みの過去・当月明細は `transactions` にそのまま保持）。 |
| **貯蓄目標 (`savings_goals`)** | **未達成: 物理削除 / 達成済: 論理削除 (アーカイブ)** | 未達成目標のみ物理削除可能。達成済み（達成率100%以上）目標は削除不可とし、`is_archived = true` でアーカイブ保護（一覧トグルで閲覧・進行中への復元が可能、合算進捗集計からは除外）。 |
| **家庭アカウント全体の退会** | **物理完全抹消** | 個人情報保護のため、該当世帯スキーマ（`DROP SCHEMA tenant_xxx CASCADE`）を物理完全抹消。 |
| **新規世帯登録申請の却下・抹消 (`households`)** | **論理状態保持 / 任意物理削除** | 却下時は `status = 'rejected'` として履歴保持（システム管理者による再承認が可能）。管理者が「削除（抹消）」を実行した場合は申請世帯・所属および他世帯所属のない申請ユーザーを物理削除し、同一メールアドレスでの再申請を可能化。 |
